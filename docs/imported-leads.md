# Imported lead lists and workspace preview

Imported rosters use `outreach_lead_lists` and `outreach_imported_leads`, separate from provider campaigns, synchronization state, conversations, and results analytics. A compound list/client foreign key prevents cross-client assignment. Service-only tables have RLS and explicit grants; clients read only the existing membership/feature-authorized directory RPC. The RPC unions campaign and imported rows before global filters, counts and deterministic 36-row pagination.

The directory adds `list` (optional UUID query), `lists` filter options, and nullable `listId`/`listName` on rows. Campaign rows have a campaign identity and null list; imported rows have a list identity and null campaign. Lists are capped at 500 visible choices, plus an authorized selected choice. Search and counts always cover the full workspace. Old campaign results views are unchanged.

`prepareLegacyLeadImport` is an operator-only adapter for a reviewed legacy JSON schema, not a public upload API. Callers must pin the exact file hash and authorize the target. It produces deterministic row UUIDs, hashes source identity, normalizes display text, deduplicates email/profile identity within a list, and emits aggregate diagnostics. No real lead fixtures are committed. Retry via upsert on the primary key; do not prune existing data or silently replace a source hash.

The reviewed Chris roster contains 10,225 rows at source SHA256 `6d9bb04e3ff10936fb8434b955961b90d47333075116877d2eca95de650cd814`. It has 10,225 distinct valid email addresses. The source's generic `verified` flag denotes a previous LinkedIn/current-role check, not email deliverability. Only that explicit flag plus a safe profile URL and nonempty source reason may preserve LinkedIn verification, with private evidence labeled as an imported prior check. Email verification remains unknown because the flattened source does not retain structured native status evidence. The existing strict ASCII profile-link allowlist makes 22 non-ASCII/encoded URLs unavailable; all contacts remain in the import. No new provider verification was performed.

The `client_outreach_workspaces` view adds `presentation_mode` from the existing feature config: exactly `preview` selects preview, otherwise live. This never grants entitlement. Preview replies are blocked in the existing locked authority helper called at enqueue, claim, and dispatch, including for agency owners and even when a real sender is accidentally configured. Conversation projections also report `canReply=false` and `canTakeover=false`. Team access management remains real; preview UI simulations must stay separate from production mutations. Leaving preview requires an explicit feature-config transition plus real provider setup.

Rollout: apply migration 0102 to the dedicated outbound database, deploy backend, provision only the authorized tenant/Auth membership, then insert the reviewed list and adapter rows. Provisioning/import scripts must separately guard the project reference, source hash/count, exact tenant/list IDs, and emit no contact values or credentials. This migration does not seed tenants, import production leads, connect accounts, call providers, or send messages.

## Review priority and escrow

Migration 0105 adds a service-managed `review_state` to imported contacts. `client` preserves existing visibility; `escrow` retains the original row and list assignment while excluding it from the client directory. Filtering happens inside the authorized database RPC before search, totals, company choices, list choices and pagination. It applies equally to agency users previewing the client view. Lists containing only escrow contacts are omitted; legacy empty-list behavior is retained. Campaign rows and other tenants' rosters are unchanged.

The dedicated `GET /api/outbound/leads/escrow?clientId=<uuid>&q=&page=1` calls `list_outreach_escrow_leads` with the authenticated user's bearer. Only an active agency owner or an explicitly assigned operator can use it. Client admins, members, viewers and unassigned users are denied. Feature suspension and revoked memberships take effect on each request. No browser role receives access to the raw tables or a release mutation.

`priority_rank` is unique within a client and requires review time and a fit reason. Escrow requires a review reason and time, with no active priority rank. The normal directory defaults to `priority` sorting and retains explicit company/name/role sorts. Legacy unranked contacts fall back to company ordering. The API adds optional `priorityRank`, `fitReason`, `emailValidation`, `contactPreference`, `researchGaps`, `researchedAt` and `sourceUrls` fields without removing old fields. Only those allowlisted metadata keys are projected; raw research receipts and arbitrary evidence remain private. Source links accept HTTPS domain URLs without credentials, IP addresses, query parameters or fragments.

Email validation and buying fit are separate. A reviewed valid email may be marked `verified` only with actual verification evidence; risky/catch-all and unknown results are not marked verified. `researchGaps` retains uncertainty about role freshness, company size and demand. A priority rank is not proof of buying intent.

The migration itself changes no client's selection. A subsequent operator-reviewed transaction must pin the source roster and selection hashes, assert every original identity/list assignment, preserve the complete inventory and set both selected and escrow states atomically. It must produce an aggregate receipt and a local rollback artifact before applying. The current Ice Shaker request is scoped to the reviewed 1,000 contacts; the other 9,225 original contacts, including the 62 weak fits, remain in escrow for further review.
