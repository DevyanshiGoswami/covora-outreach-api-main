# Campaign sequence review

Native campaign plans now expose persisted sequence variants for review. The new
`outreach_campaign_plan_sequences` table is separate from provider campaigns,
senders, recipients, enrollments and dispatch work. It cannot activate a plan.
The migration creates no client content and changes no existing lead rosters.

The table allows only service role writes. A composite foreign key binds each
variant to its plan, tenant and channel. Raw table access is denied to end users,
including agency owners. The existing authenticated campaign list RPC still
checks the workspace feature and active membership, then returns only neutral
review fields. Source file, version and hash stay server side. Preview workspaces
use the same read authorization as other workspaces.

Bodies and placeholders remain plain text and are not personalized by this API.
Email steps require an initial subject on day zero, chronological offsets and
explicit followup threading. LinkedIn steps use `after_connection` and may have
null timing because the source may not specify a delay. No connection request
or followup is inferred. Variant ordering and step positions are deterministic.
Content, step counts, labels and control characters are bounded in both the
schema and response validator. The frontend must render this content as text.

The list endpoint adds `sequenceVariants`; the selected plan summary on the
lead directory is deliberately unchanged. This avoids extra sequence reads on
every page or filter change. Older clients can ignore the new list property.

Validation used a newly created local stack `Covora_EPM_Sequences_20261027` on
ports 62621 and 62622. Existing stacks were not reset or changed. The ignored
`.artifacts/sequence-db-20261027` checkout adjusts only local test target guards
and generated environment setup to these isolated ports. Public database types
were generated by the repository script against that schema, then copied back.
Unit coverage checks exact copy, neutral projection, malformed content, timing
and threading. Database coverage additionally checks all active roles, suspended
membership, disabled workspace features, other tenants, anonymous access,
raw table denial, cross tenant/channel foreign keys, malformed JSON, size bounds,
cascading cleanup and the absence of provider or enrollment side effects.
